# Proposal：在终端中与 Claude Code 和 Codex 共同讨论与工作

## 背景

同时使用 Claude Code 和 Codex 时，同一件事的讨论分散在两段会话里。用户向一方提出问题，再把回答复制给另一方；出现分歧后，还要继续转述、补充遗漏的背景。讨论越长，用户花在整理上下文上的精力就越多。

把两个窗口放在一起，只减少了切换窗口的动作，没有解决共同讨论的问题。换成普通的多模型聊天工具，又无法直接保留原有 Agent 的工具、登录、项目配置和长期背景。

本项目提供一个共同的终端会话：用户与 Claude Code、Codex 在同一处发言，能看见各自的意见，也能继续调用原生工具完成工作。应用组织交流，不替代两个 Agent。

## 目标用户

首版面向已经在同一台电脑上使用 Claude Code 和 Codex、习惯终端操作，并且经常需要双方参与同一件事的个人用户。用户已有可用的原生 CLI 和登录环境，不需要为了群聊重新配置一套模型服务。

首先适配 macOS 自带的 Terminal.app，以及由 Cockpit 管理 Codex 账号与配置的使用方式。团队协作、远程访问和其他终端平台不作为首版验收范围。

## 使用场景

### 对同一个问题听取不同意见

用户有一个需要讨论的问题，希望双方分别作出判断，而不是先让一方回答，再让另一方围绕已有结论附和或挑错。

用户一次提出问题并选择双方回答，随后看到两份带姓名的原始回复。双方使用相同的本轮问题与已有群聊内容，独立回答。用户可以向其中一方追问，也可以要求它回应另一方的观点。

### 共同推进一项工作

用户请 Claude 整理方案，再请 Codex 检查遗漏。现在需要手动复制方案，还要解释方案来自谁、哪些内容已经决定、哪些仍在讨论。

在群聊中，方案保留在原来的位置，Codex 可以接着讨论，不需要用户重新整理。讨论涉及文件或实际操作时，被指定的成员继续使用自己的原生工具；另一方不会因为看见任务就自动开始执行。

### 隔一段时间继续交流

用户离开终端后重新回来，希望接着原来的话题，而不是重新介绍参与者和之前的结论。重新打开同一个群，应能看到此前的消息，并继续双方各自的会话。无法恢复时明确提示，不在保留旧记录的同时，悄悄换成没有上下文的新会话。

这些场景共同需要的是：让讨论与工作在同一个地方连续发生，同时保留两个 Agent 的独立身份和原有能力。

## 目标

cli-common-room 是面向原生 CLI Agent 的终端群聊应用。首版完成以下流程：

1. 在 Terminal.app 中启动应用，选择现有 Claude Code 与 Codex 环境。
2. 在一个群里向指定成员或双方发送消息。
3. 阅读各自的回复，并指定下一位成员继续讨论。
4. 在同一窗口查看工具过程、回答提问、处理授权或停止执行。
5. 退出后重新进入同一个群，继续讨论。

能完成这条流程，才算形成可用产品；仅把两个模型的回答显示在一起不算完成。

## 基本概念与信息结构

群聊是一段持续交流，参与者是用户与两位成员。群里的发言默认对双方可见，点名只决定谁回答，不构成私聊。首版只处理一个活动群，不做群列表管理。

成员是接入群聊的原生 Agent。Claude Code 和 Codex 各自保留自己的会话与配置。用户看到成员名称、使用的模型，以及空闲、回答中、等待操作、已停止或连接异常等状态。

消息包含用户提问和成员原话。工具过程附在发起它的成员回复下，不作为第三个发言者；授权请求和需要回答的问题单独突出显示。

工作目录是成员读取项目文件、加载项目指令和执行任务的位置，不是群聊存在的前提。日常讨论不要求创建 Git 仓库；涉及具体工作时，用户能辨认当前目录，避免在错误项目中执行。

终端主界面由成员状态、消息记录和多行输入区组成。阅读历史时不被新回复强行拉回底部；尚未发送的输入不因回复刷新而丢失。连接异常和等待授权等信息直接可见，不要求打开另一个终端判断发生了什么。

## 产品决策

### 一个群聊窗口，不并排嵌入两个终端

并排终端最接近原有使用方式，但仍要用户承担消息转述。网页或桌面工作台能提供统一界面，却改变了终端优先的习惯。首版选择统一的终端消息流，避免在两个输入区之间切换。网页适配后置。

### 连接现有 Agent，不重新配置模型

普通 API 聊天客户端更容易统一消息格式，但需要另一套认证、工具和上下文管理，偏离保留原生能力的目标。

应用连接本机已有的 Claude Code 和 Codex，沿用各自的登录或托管环境，不新增模型 API Key 配置流程。Cockpit 继续负责账号管理；应用不复制凭据，不自动切换模型。工具、skills、MCP、hooks 和记忆分别核对，不把成功回复当成全部能力可用。

### 用户指定发言，不默认自动互聊

自动轮流讨论能减少点名，但也会增加等待和额度消耗，还可能在用户尚未决定时开始执行任务。首版采用明确指定的方式：点名一位、同时询问双方，或者指定一位回应另一位。

同时询问双方时，两者独立作答，不因为某一方先完成而改变另一方收到的问题。成员在正文中提到对方，不触发对方执行。未选接收方时保留输入并提示选择，不擅自调用双方。

例如，先发出“请双方分别判断这个方案”，得到两份答案后，再发出“请 Codex 回应 Claude 对维护成本的担忧”。第二次是明确的交叉讨论，第一次不是。

### 保留原话与分歧，不增加主持模型

由第三个模型总结双方意见，会再次引入转述，也增加调用成本。群聊直接展示各自原话，用户决定继续追问、采用哪条意见或结束讨论。

工具输出默认只在对应成员的执行记录里展示，不自动整份交给另一方。需要讨论某个结果时，由用户明确引用，避免无关日志和敏感内容进入双方上下文。

### 连续会话与长期记忆分别保留

同一个群重新打开后，延续此前的双方会话；新建群则从新会话开始，不因账号相同就假定继承历史讨论。

长期记忆继续由原生 Agent 管理，不另建共享人格或记忆库，也不自动合并私人历史。工作目录变化可能影响加载的背景与工具，需要在接入时说明。外部历史会话导入不进入首版。

### 在群里完成工具交互

只展示回答、遇到授权就返回另一个终端，会中断使用流程。工具过程、授权和提问必须能在群聊窗口处理，操作明确归属对应成员，并遵守原生环境的权限规则。

拒绝授权后不得改用自动批准重试。停止一位成员不影响另一位，已经发生的文件修改不因停止而撤销。同一目录中的执行类任务按顺序推进，不把双方可同时讨论扩展成可同时修改相同文件。

## 首版范围

包含两位原生成员的接入、单群文字交流、指定发言、独立回答与交叉回应、工具过程、授权与提问、停止和退出恢复。中文输入、多行粘贴、历史滚动和窗口缩放属于基本可用性，不作为后续美化项目。

不包含网页与手机、远程服务、多用户、自动互聊、第三个主持模型、账号池、外部历史导入、附件、多项目管理及插件市场。Ghostty 及其他终端的兼容适配放到首版稳定后，不作为首版依赖或验收条件。

## 验收标准

| 场景 | 完成标准 |
| --- | --- |
| 现有环境接入 | 从 Terminal.app 启动，双方通过原有登录或托管接入真实回复；不要求另填模型 Key，原配置未被覆盖 |
| 同题独立回答 | 只输入一次问题，得到双方原话；先完成的一方不会成为另一方本轮的前置答案 |
| 指定交叉讨论 | 指定另一位回应后，无需复制粘贴即可接续上文；未被指定的成员不执行 |
| 共同工作 | 各成员分别完成受控的真实工具调用，过程和结果归属清楚 |
| 授权与提问 | 实际触发的授权和提问均可在群中处理；拒绝、取消及迟到的回答不会作用到错误成员 |
| 停止与异常 | 能停止指定成员；失败有明确状态，部分回复不显示为完成，执行状态不明时不自动重复任务 |
| 会话继续 | 退出重开后继续同一话题；恢复失败明确提示，不静默创建替代会话 |
| 终端使用 | Terminal.app 中中文输入、多行粘贴、滚动与缩放可用，长回复不破坏尚未发送的输入 |

验收使用真实 CLI 与隔离的工作材料。兼容性清单区分已验证、未验证和不可用的能力，不以模拟回复或静态界面替代实际链路。

## 后续设计与实现

先验证原生接入中的授权、提问和会话连续性，再建立可编译的模块骨架，最后在真实终端完善交互与恢复。具体模块和协议边界见 [架构与开发顺序](ARCHITECTURE.md)。

文字方案确定后制作终端交互原型，验证消息阅读、输入和授权处理，在 Terminal.app 中直接体验，不截图。协议实验或原型若不能满足上述流程，先调整相应设计，不通过削减原生能力掩盖问题。
