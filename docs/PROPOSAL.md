# Proposal：原生 CLI 群聊

状态：待用户过目。本文是开发依据，不代表功能已经实现。

## 要解决的问题

用户已经在使用 Claude Code 和 Codex。两者各自拥有登录状态、工具、配置、长期背景与会话记录，但交流时需要用户手动转述另一方的意见。

这个项目提供一个终端群聊窗口，让用户能直接看到双方原话，并让双方在明确指派后回应彼此。底层继续使用真实的原生 Agent，不用模型 API 重新实现一套助手。

首个使用场景是：用户在 Ghostty 打开群聊，向双方问同一个问题，分别看到回答，再指定其中一方阅读另一方的意见并回应。聊天可以是日常讨论，也可以涉及实际工作，不强制围绕代码仓库展开。

## 已确定的方向

- 终端优先：一个群聊界面，不是两个终端并排，也不是网页套桌面壳。网页适配后置。
- 使用本机原生 Claude Code、Codex；应用只承担交互、消息转交和会话管理。
- 不要求另购模型 API 服务或填写模型 API Key；沿用用户已有原生登录或托管接入。订阅可用性和费用归属必须验证，不能由“不填 Key”推断。
- 支持 Ghostty 中启动；Codex 的配置目录、程序路径可指向 Cockpit 托管实例。应用不接管账号管理。
- 工具、skills、MCP、hooks、记忆是需要保留并逐项核对的能力，不用“模型能回答”代替完整接入验收。
- 不静默换模型、不覆盖原生系统提示、不为接通而关闭工具或绕过审批。

## 第一版如何使用

以下是拟议交互规则，命令名称不是已经实现的 API。

| 用户动作 | 预期行为 |
| --- | --- |
| `@claude 你怎么看这个方案？` | 只唤醒 Claude；Codex 不执行本轮 |
| `@codex 请回应 Claude 刚才的意见` | 交付尚未同步的群消息，由 Codex 回应 |
| `@all 分别说说你的判断` | 双方收到截至本次提问的同一份群聊快照，独立回答，不因先后完成而看到本轮对方答案 |
| 不指定成员直接发送 | 保留输入，提示选择目标，不擅自调用两边 |
| Agent 在回答中提到另一位成员 | 只显示文字，不自动触发下一轮 |
| 用户停止某位成员 | 请求取消该成员当前轮次，显示实际停止状态，不影响另一位 |
| 工具要求授权或 Agent 向用户提问 | 在同一窗口展示，回答送回对应成员和轮次；普通群消息不充当批准 |
| 退出后重新进入 | 恢复群记录和两条原生会话的关联；无法恢复时明确报错，不伪装成同一个会话 |

群消息对双方可见，`@` 只决定谁执行，不是私聊权限。尚未被唤醒的成员在下次发言前才收到新增消息；私人话题应在原生独立会话中处理。

双方是两个独立成员，不设置一个替另一方总结的主持模型。展示原话，保留不同意见；工具结果不默认整份转交给另一个成员。

## 界面需要表达什么

一个消息流、一个多行输入区、一条成员状态栏。消息带发言人，工具过程可展开，授权与提问有明确的等待状态。

Ghostty 中需验证中文输入法、多行粘贴、滚动、窗口缩放、长回复和取消。先把文字行为定清，再在真实终端试用可交互原型；不截图，不以静态排版代替使用验收。具体 TUI 库留给技术验证选择。

## 连续性与能力边界

新建群聊就是新会话，不能因为账号相同就宣称继承过去的全部对话。第一版优先支持群内新建会话的连续使用和恢复；导入外部历史会话后置。

长期记忆仍由原生环境读取和维护，群聊应用不另造共享人格库。工作目录可能影响记忆、项目指令和工具加载，配置时必须说明这种差异。保留原生工具也不等于保留原生终端的每个快捷键或内置命令；未支持能力逐项披露，不能笼统称为“满血”。

## 本期不做

网页与手机远程访问、云服务、多用户、自动互聊、第三个协调模型、账号池与凭据代理、插件市场、自动导入私人历史、多项目任务看板。第一版只做一个用户、一个活动群、两个成员；不额外造 Agent 执行工具。

首版不承诺多个成员安全地同时修改同一目录。日常聊天无须写权限；执行类请求仍遵守原生权限，涉及共享工作区写入时串行执行或使用用户明确选定的独立工作区。

## 为什么这样选

两个原生终端最容易保留交互，却仍需要手动搬运消息，不满足单窗口群聊需求。已有多 Agent 工作台接近目标，但其界面、默认权限和固定 CLI 版本未必适合现有环境。重做模型 API 客户端会丢失原生 Agent 能力，也违背不另配模型 Key 的要求。

因此选择轻量终端客户端加原生协议适配；代价是需要处理两套事件、审批和恢复机制。这部分是接入成本，不能靠解析终端显示文字或自动同意权限请求省掉。

## 怎样算完成

- 在 Ghostty 的同一群聊窗口完成点名、双方独立回答和指定回应；双方身份不混淆。
- 两边各完成一次真实工具调用、一次实际触发的审批或交互请求，以及一次取消；拒绝后不自动重试为批准。
- 退出重开后继续同一群和对应原生会话，不重复执行上一轮任务。
- 列出 CLI 版本、模型、接入方式与工具能力验证结果，区分已验证、不可用和未验证。
- 原有 CLI 配置、凭据和记忆不被应用复制或覆盖；公开仓库不包含个人路径、聊天内容与密钥。

## 开发方式

这是个人项目。用户过目后即可把设计作为基线，不另设评审会、设计草案 PR 或默认子代理评审。设计文档直接随仓库维护，重要变化在 Git 和对应 Issue 中留下理由。

实现仍按小任务走 Issue、分支、验证和关联 PR，避免直接修改 main。不为已授权的常规步骤重复询问；新增费用、扩大权限或改变产品方向时说明影响。自动化完成不等于用户已验收。

技术边界和实现顺序见 [架构说明](ARCHITECTURE.md)。
