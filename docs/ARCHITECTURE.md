# 架构与开发顺序

状态：待用户过目；当前仓库仅有文档，没有运行实现。产品边界以 [Proposal](PROPOSAL.md) 为准。

## 1. 架构原则

本机应用连接两个原生 Agent，不重新实现它们的工具执行、认证刷新、上下文压缩和记忆系统。协调层负责“谁收到什么、哪一轮正在执行”，界面负责展示与用户输入，适配器负责原生协议。

```text
Ghostty 内的群聊 TUI             后续网页客户端
           │                         │
           └──── 应用命令与事件 ──────┘
                         │
                    会话协调层
                   /     |     \
              本机存储   |   运行环境配置
                  ┌──────┴──────┐
             Claude 适配器    Codex 适配器
                  │             │
             原生 CLI 进程   原生 app-server
```

第一版一个本机进程承载界面和协调层，通过函数调用与事件传递连接，不先建 HTTP 服务或后台 daemon。原生 Agent 是独立子进程。以后网页只增加传输与展示层；远程暴露、鉴权和后台存活策略另作设计。

## 2. 技术选择与边界

| 项目 | 当前提案 | 不在此刻锁定的部分 |
| --- | --- | --- |
| 语言与运行时 | TypeScript、Node.js | 最低版本在协议实验后固定并写入工程配置 |
| 终端界面 | 单消息流 TUI，Ghostty 为首个验收终端 | Ink 是候选，先比较中文输入、粘贴和滚动表现 |
| Claude 接入 | 本机 Claude Code 的程序化流式接口 | 双向审批、提问及所需支持方式必须实测后定稿 |
| Codex 接入 | 本机 `codex app-server` 的公开协议 | 按实际安装版本验证；不默认下载另一版本 |
| 群聊持久化 | 本机 SQLite，便于事务保存消息与交付状态 | SQLite 驱动和 schema 在恢复语义验证后确定 |
| 测试 | 纯协调逻辑测试、协议夹具、隔离的真实 CLI 验证 | 不让普通测试调用账号或消耗模型额度 |

这些是拟议技术选择，安装了依赖不代表架构已成立。首个工程 PR 才引入必要依赖并锁定版本；不引入通用 Agent 框架、模型路由服务或分布式消息队列。

## 3. 模块职责与依赖

以下是拟议模块，尚未创建目录。

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| `terminal` | 输入、消息显示、状态、审批与提问交互 | 拼接原生协议、操作会话数据库 |
| `room` | 目标选择、消息交付、轮次状态、取消与恢复决策 | 直接启动 CLI、运行工具、替用户批准 |
| `adapters/claude` | Claude 协议、事件映射、原生会话恢复 | 替换 Claude 系统提示或工具集 |
| `adapters/codex` | app-server 协议、线程与审批映射 | 接管 Cockpit 账号或 provider |
| `storage` | 群消息、原生会话引用、交付状态 | 拷贝原生 SQLite、凭据或私人记忆 |
| `runtime` | 程序路径、工作目录、环境、子进程生命周期 | 自动安装 CLI、自动登录或升级 |

协调层只依赖自己的消息类型和适配器、存储接口，不依赖 TUI 或具体协议包。入口组装依赖。原生字段留在适配器内部，无法无损表达的新交互返回明确的“不支持”，不得当普通文本丢弃。

## 4. 原生接入与能力核对

Claude 的程序化接口提供流式事件与会话继续能力；官方同时说明它与终端交互有差异，部分命令不可用。Codex app-server 提供线程和轮次操作，以及由客户端回复的审批请求。这支持采用协议适配，但并不证明两个入口具备全部原生终端功能。

验证环境必须使用实际的可执行文件、工作目录、配置目录和模型设置。禁止以 `--bare`、安全精简模式或工具禁用开关掩盖接入问题，也不默认开启完全访问或跳过审批。原生环境本身已有的权限规则应如实显示，不能声称每次工具调用都会弹出审批。

| 能力 | 必须获得的证据 |
| --- | --- |
| 认证与模型 | 由原生程序报告接入状态，实际完成一次请求；核对模型，不通过成功响应猜测计费来源 |
| 文件与命令工具 | 在隔离目录完成真实读操作及受控命令；只读测试不扩权 |
| 审批与用户提问 | 请求可展示、正确回传；批准、拒绝、取消不会串到另一成员或轮次 |
| MCP、skills、hooks | 与同工作目录的原生入口核对，执行无敏感数据的受控样例，不把配置存在当作已加载 |
| 记忆与项目指令 | 验证加载路径及作用域，不读取或导入私人内容作为测试样本 |
| 连续会话 | 两轮交流、取消、正常退出恢复和异常中断分别验证 |
| 宿主附加能力 | 区分 CLI 自带与外部宿主注入；后者不承诺自动迁移 |

兼容性结果按 CLI 版本、接入环境和能力记录。协议或 CLI 升级后，只复测受影响的路径；不从某个版本的结果外推所有版本。

## 5. 消息交付与身份

一个群对应两个独立的原生会话。应用记录群 ID、成员 ID、原生会话 ID、环境引用和交付进度；同名成员在不同群里不能共用原生会话。

群消息包含稳定 ID、顺序号、发言人、正文及产生它的轮次。用户指定的执行目标单独记录，不能靠扫描任意消息里的 `@` 自动派发。别的成员发言作为带来源的上下文，不作为用户授权或系统指令；明确来源只能减少混淆，不能保证消除提示注入风险。

每次执行冻结一份输入快照，只交付该成员尚未收到的群消息。它在原生会话中已经产生的自身回复只建立映射，不再作为新用户输入重复灌入。文本保持原话；工具参数和输出默认不跨成员转发，用户需要时明确引用。第一版仅承诺文本，附件协议另议。

`@all` 的两个轮次共享同一快照边界。即使其中一方先完成，另一方也不收到本轮答案；想回应对方必须由用户再发起一轮。

每个成员最多一个活动轮次。忙碌时保留新输入并提示等待或停止，不静默启动第二个进程；跨成员可以并发讨论，但不因此授权同时写同一工作区。

## 6. 最小接口语义

以下为应用内部拟议契约，不是声称上游具有同名 API，也暂不固定 TypeScript 签名。

- 连接：接收本机运行环境和可选的原生会话引用，返回已验证能力与连接状态。
- 开始轮次：接收成员、轮次 ID、带来源的输入快照；返回流式事件，不擅自新建或切换账号。
- 响应交互：必须携带成员、轮次和请求 ID，只接受当前未解决请求允许的选项。
- 取消轮次：发送原生取消请求，等确认或报告状态未知，不能只停界面动画。
- 关闭：停止接收新输入，处理未决交互，持久化状态，释放本应用拥有的连接与进程。

统一事件至少区分：文本增量、工具开始与结果、权限请求、用户提问、原生会话关联、轮次完成、取消、失败、连接丢失。交互请求保留原生选项和必要语义，不能都压成“允许／拒绝”。只有明确的完成事件才算本轮成功。

## 7. 失败、重试与恢复

运行状态分为待命、执行中、等待交互、停止中，以及完成、失败、已取消、状态待核对。进程退出或连接断开不等于任务从未执行。

群输入和待发送记录先保存，再发送给原生进程；收到能够确认接收的原生证据后，更新交付状态。任务完成与输入接收分开记录，不能等到整轮成功才决定是否需要重送。

如果发送后断线，无法判断对方是否收到，就标记待核对。恢复时优先读取原生历史或状态进行对账；无法可靠对账则提示用户选择，不自动重送可能已经执行的写入。第一版不宣称跨两个系统实现 exactly-once。

取消不能回滚已经发生的文件修改。已经显示的部分回复保留为“未完成”，不会自动当作完整答案交付给另一成员；用户可明确引用。未决审批在取消或断开后失效，迟到的按钮操作必须拒绝。

同一原生会话由一个入口拥有写入权；应用内部防止重复连接，无法确认外部终端是否仍在使用时不接管旧会话。首版只恢复本应用创建并记录的会话；跨入口共享和外部历史导入另作设计。

## 8. 配置、隐私与进程边界

程序路径、工作目录、模型选择和配置目录引用保存在 Git 外的本机配置中。Codex 可显式指定 `CODEX_HOME`；Cockpit 仍负责账号与 provider，应用不复制、解析或刷新其认证文件。

运行环境在启动时解析并固定于会话，不能随意跟随外部账号切换。重启后环境不一致时先提示，不能拿新账号默默继续旧会话。必要环境变量可以传给原生子进程，但不整份打印或持久化；两个成员的配置分别生效。

启动前让用户确认可信工作目录和配置来源，尤其是可能执行的 hooks、插件与 MCP。应用自身的审批界面不能阻止原生环境在启动阶段执行所有钩子，不应宣传成安全沙箱。

群记录和原生状态分开存储；本机数据目录限制访问权限，错误日志默认不含聊天正文、环境值、原生认证响应。诊断导出显式选择并脱敏，不把目录权限等同于磁盘加密。不默认向遥测服务发送内容。

子进程用程序路径和参数数组启动，不把用户文本拼进 shell。退出时仅处理本应用启动的进程，不能通过进程名批量杀掉用户其他 CLI。终端显示须处理不可信控制字符，避免把工具输出直接当终端控制序列执行。

## 9. 开发顺序与交付条件

| 顺序 | 工作 | 进入下一步所需证据 |
| --- | --- | --- |
| 0 | 用户过目 Proposal 与本架构 | 确定首版边界；未决技术点保留，不伪装成已通过 |
| 1 | 隔离的原生协议实验 | 双方真实回复、审批或提问回传、取消、会话继续；验证现有登录与托管环境，失败先调整设计 |
| 2 | 可编译架构骨架 | 入口、协调层、适配器和存储接口串联；测试夹具只能用于测试，产品入口不可伪造模型回复 |
| 3 | 最小真实终端群聊 | Ghostty 中完成点名、独立回答、指定回应；中文输入、粘贴、滚动和交互可用 |
| 4 | 持久化与恢复 | 正常退出、异常断开、待核对交付与过期审批均有测试；不重复执行任务 |
| 5 | 首版交付 | 能力清单与限制明确、使用说明可复现；通过验收后再打版本并考虑网页适配 |

每阶段拆成边界明确的小 Issue，不预先铺满未来任务。先写能暴露具体错误的测试，再实现对应行为。协议夹具不能代替真实接入证据，真实账号测试默认不进 CI；记录脱敏后的结果即可。

本地验证按改动选择最小充分集合，不能照搬其他仓库的全量检查。TUI 在真实终端中验收，不为终端项目额外制作网页演示，不截图。每个实现 PR 说明改动、原因、验证及未完成项；不重复设置评审仪式。

## 10. 实现前必须解决的问题

1. Claude 程序化接口中，审批、用户提问和 MCP 交互如何完整回传？若需 SDK，它是否仍调用指定的原生程序、遵守原有认证边界？未验证前不选定。
2. 两套实际安装版本能否保留所需配置和插件？Cockpit 托管环境是否有额外宿主能力，哪些无法从 CLI 获得？
3. 现有登录用于本机应用的方式是否符合官方支持范围？接入成功不等于订阅计费或分发方式得到保证；不提取 OAuth 凭据直连模型接口。
4. 原生接收确认与恢复状态能否支撑可靠对账？不足时采用显式待核对，不实现盲目自动重试。
5. 候选 TUI 库能否满足 Ghostty 中的中文输入与长消息操作？用可运行样例判断，不依据组件清单决定。
